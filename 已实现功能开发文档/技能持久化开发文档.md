# 我方角色技能持久化 — 开发文档

> 目标：让我方角色的技能配置（含属性、职业、特效等）持久化存储在 SillyTavern 的**聊天记录 JSON** 中。
> 清空 `combatstatus`、刷新页面后，同名角色的技能依然存在；在酒馆中**新建聊天对话后技能消失**（因为新聊天文件无此数据）。

---

## 1. 背景与需求

### 1.1 现状问题
- 当前所有角色/技能数据只存在于浏览器内存（`heroesData` / `enemiesData`），刷新即丢。
- 每次战斗都需要 LLM 重新通过 `<Combat_block>` 传递技能，且每次的数值可能不一致、无法按玩家喜好固定。
- localStorage 以浏览器地址为依据、跨聊天共享，会导致"不同角色卡/不同聊天的角色技能串味"——**不可用**。

### 1.2 目标行为
1. 我方角色技能持久化到**聊天记录 JSON**（`chat_metadata.variables`）。
2. **清空 `combatstatus` + 刷新** → 同名角色技能仍在。
3. **新建聊天对话** → 技能消失（新聊天无此数据）。
4. 保存时机：**只有玩家在技能编辑器点击"保存"** 才写入聊天文件。**首次初始化也需要玩家点一次保存**，才会写入。
5. 合并方向：**持久化优先**（详见 §5）。

### 1.3 明确不做（范围）
- **敌方角色不持久化**（敌人数量多、每次战局都不同，交给 `Combat_block` 动态生成）。
- 本次**不动 LLM 设置持久化**（其 `setVariables` bug 已记录，见 §6.1，留待后续单独处理）。

## 2. 技术方案：使用酒馆助手 `chat` 类型变量

### 2.1 为什么选 `chat` 类型
酒馆助手（JS-Slash-Runner）提供 6 种变量类型，存储位置与生命周期如下：

| type | 存储位置 | 生命周期 | 是否满足需求 |
| :--- | :--- | :--- | :--- |
| `global` | 用户存档 | 全局永久 | ✗ 跨聊天共享 |
| `character` | 角色卡 | 随角色卡导出 | ✗ 换卡即换 |
| **`chat`** | **聊天 JSON 的 `chat_metadata.variables`** | **随聊天文件导出** | ✅ **符合需求** |
| `message` | 某条消息楼层 | 随楼层 | ✗ 读取时机复杂 |
| `script` | 脚本 | 随脚本导出 | ✗ 不适用 |
| `extension` | 用户存档（扩展ID下） | 全局 | ✗ 跨聊天共享 |

**结论：使用 `type: 'chat'`。** 数据写入 `chat_metadata.variables`，随聊天 JSON 一起保存/导出/导入，完美满足"聊天内持久、新建对话即消失"。

### 2.2 官方 API
- **读取**：`getVariables({ type: 'chat' })` → 返回 `Record<string, any>`（同步，无需 `await`）。
- **写入**：`replaceVariables(新表, { type: 'chat' })` —— 整体替换整个聊天变量表。
  - ⚠️ 因此**不能直接整体替换**（会覆盖聊天里其他插件存的变量）。安全做法是先用 `getVariables` 取回旧表、`_.set` 我们的键、再 `replaceVariables` 写回。
  - 或使用 `insertOrAssignVariables(变量, { type: 'chat' })` —— 内部就是"取回→合并→整体替换"，天然只更新传入键，更安全。

> 文档依据：`JS-Slash-Runner-Doc` 的 `变量/变量类型.md`、`变量/获取变量.md`、`变量/替换或修改变量.md`。
> 类型定义：`JS-Slash-Runner/@types/function/variables.d.ts`。

## 4. 目标实现设计

### 4.1 存储结构（单一键）
```js
const ROSTER_VAR_KEY = 'rpg_combat_roster';
// chat 变量中的值：
{
  version: 1,
  heroes: [ /* 清洗后的我方角色对象 */ ]
}
```

### 4.2 角色对象序列化（字段白名单）
> 不能直接存整个 `heroesData` 元素——含 `dom`（DOM 引用，JSON 序列化会失败/巨大）、`buffs`、`isDefending`、`hitBonus`、`shield` 等运行时战斗状态。只存"角色配置 + 技能集"。

**存储结构**（每个角色）：
```js
{
  name: '角色名',                 // 唯一键
  config: {                       // 角色配置字段
    img, classType, isWise, maxHp, maxMp, maxTp, atk, def, spd, actCount
  },
  skills: [ /* 技能对象数组 */ ]   // 完整技能集（玩家保存时的版本）
}
```

**技能对象字段**：`name, isReaction, reactionTarget, kanpoTarget, damageType, fxTag, cost, hpCost, tpCost, hit, turns, type, power, type2, power2, type3, power3`

> 不保存 `hp/mp/tp` 当前值（属战斗状态，加载时由 `Combat_block` 提供当前值）。

### 4.3 新增函数
```js
// 1. 序列化：heroesData → 可存对象数组
function serializeHeroesForSave() { /* 白名单过滤 */ }

// 2. 写入：saveEditor 内调用，把清洗后的我方阵容写入 chat 变量
function persistHeroesRoster() {
  const payload = { version: 1, heroes: serializeHeroesForSave() };
  // 直接依赖酒馆助手，无降级（§6.6 已删除，前端无酒馆助手无法运行）
  insertOrAssignVariables({ [ROSTER_VAR_KEY]: payload }, { type: 'chat' });
}

// 3. 读取：从 chat 变量读回 payload（含状态/版本校验）
function readRoster() {
  try {
    const vars = getVariables({ type: 'chat' });
    const payload = vars && vars[ROSTER_VAR_KEY];
    if (payload && payload.version === 1 && Array.isArray(payload.heroes)) return payload;
    return null;
  } catch(e) { return null; }
}

// 4. 读取+合并：在 buildCombatDataFromYAML 成功后、initUI 前合并
function applyPersistedRoster() {
  const payload = readRoster();            // 从 chat 变量读 payload
  if (!payload) return;
  // 对 heroesData 中每个角色 h：
  //   通过 h.name 找到持久化角色 r
  //   → 配置字段用 r.config 覆盖（保留 id/当前 hp 等战斗字段）
  //   → 技能集 = r.skills（持久化基准）+ Combat_block 新增技能（追加）
  //   找不到同名 r → 保持 Combat_block 原样
}
```

### 4.4 改动点清单
1. 新增 `ROSTER_VAR_KEY` 常量 + 上述 3 个函数（放在防御设置持久化区块附近）。
2. `saveEditor()`：在 `syncEditorDataToMemory()` 之后、`persistDefendSettings()` 附近，追加 `persistHeroesRoster()`。
3. `onCombatDataReceived()`：在 `buildCombatDataFromYAML()` 成功返回 `true` 之后、`initUI()` 之前，调用 `applyPersistedRoster()`。

## 5. 合并规则（持久化优先 + 技能按名合并）

加载时 `applyPersistedRoster()` 按**角色名**（`name`）找到同名角色，再在角色内部**按技能名**合并。规则如下：

### 5.1 角色级
| 场景 | 处理 |
| :--- | :--- |
| 同名角色存在于持久化 | 配置字段（属性/职业/头像等）以**持久化版本**为准 |
| 同名角色不存在于持久化 | 保留 `Combat_block` 原版（新角色用默认技能） |
| 持久化角色不存在于 `Combat_block` | 不加入战场（`Combat_block` 决定本场出战名单） |

### 5.2 技能级（同名角色内部，关键规则）
对同名角色，最终技能集 = **持久化技能集 + Combat_block 新增技能**：

1. **同名技能**（技能名匹配）→ 以**持久化版本**为准（覆盖 `Combat_block` 的同名技能）。
2. **持久化中没有、但 `Combat_block` 有的技能** → **追加**进战局，**不能因为持久化没有而舍弃**。
3. 持久化中有、`Combat_block` 没有的技能 → 保留（它来自玩家此前的保存）。

> **一句话**：玩家改过的技能保持玩家的版本；`Combat_block` 带来的新技能一定能进战局。

> 合并时只处理"配置字段"，保留 `Combat_block` 提供的 `id`、当前 `hp/mp/tp`、`isAlive`、`buffs` 等战斗态字段，避免破坏战斗进行中的状态。

### 5.3 `applyPersistedRoster()` 伪代码
```js
function applyPersistedRoster() {
  const payload = readRoster();            // 从 chat 变量（data 前缀）读
  if (!payload) return;
  const savedByName = new Map(payload.heroes.map(h => [h.name, h]));
  heroesData.forEach(h => {
    const saved = savedByName.get(h.name);
    if (!saved) return;                     // 角色不同名 → 保留 Combat_block 原版
    // 1) 配置字段以持久化为准
    Object.assign(h, saved.config);         // 含属性/职业/头像（不含战斗态字段）
    // 2) 技能：以持久化技能集为基准，追加 Combat_block 新增技能
    const finalSkills = saved.skills.slice();               // 持久化技能
    h.skills.forEach(cbSkill => {
      if (!finalSkills.some(s => s.name === cbSkill.name)) {
        finalSkills.push(cbSkill);           // 持久化没有 → 追加 Combat_block 技能
      }
    });
    h.skills = finalSkills;                  // 同名技能已被持久化版本覆盖
  });
}
```

## 6. 潜在 Bug 与规避

### 6.1 【已确认】现有 LLM 持久化 bug（本次不动，仅记录）
- 当前 `persistLLMSettings()` 用 `setVariables({...}, {type:'character'})`。
- 酒馆助手**源码中不存在 `setVariables` 函数**（正确写入函数是 `replaceVariables`/`insertOrAssignVariables`/`updateVariablesWith`）。
- 因此 `typeof setVariables === 'function'` 恒为 `false` → 落入 catch → 静默降级到 localStorage。
- 这解释了"更换角色卡后 LLM 信息依然存在"——它其实存的是 localStorage，与角色卡无关。
- **规避**：本次新增代码**不使用 `setVariables`**，改用 `insertOrAssignVariables`。

### 6.2 chat 变量整体替换覆盖风险
`replaceVariables` 是整体替换整个聊天变量表。若直接调用会覆盖其他扩展存的聊天变量。
**规避**：用 `insertOrAssignVariables`（内部取回→合并→替换），只更新 `ROSTER_VAR_KEY`。

### 6.3 序列化含 DOM/循环引用
`heroesData` 元素有 `dom`（DOM 节点），直接 `JSON.stringify` 会失败或产生巨大输出。
**规避**：白名单字段序列化（§4.2）。

### 6.4 合并覆盖战斗中的当前状态
若在战斗进行中点保存，可能把 `hp/mp` 当前值一起覆盖，导致回血/状态异常。
**规避**：序列化白名单**不含** `hp/mp/tp` 当前值；合并时只覆盖配置字段，保留战斗态。

### 6.5 同名角色重名歧义
若两个角色叫同名（如两个"剑士"），按名匹配会互相覆盖。
**状态：本次暂缓**（用户明确要求避免单次修改过多、防止 bug 难定位）。当前以 `name` 为唯一键，文档注明"角色名需唯一才能正确持久化"；如需支持重名，后续可用新增唯一 id 字段扩展。

### 6.6 酒馆助手未安装/不可用
**已删除，未来也不实现。** 该前端脱离酒馆助手无法运行，无降级可避免 localStorage 清理麻烦。持久化只依赖酒馆助手 `chat` 变量，无兜底守卫。

### 6.7 异步执行顺序
`onCombatDataReceived` 是同步流程，`getVariables` 是同步函数，合并必须在 `initUI()` 前完成，否则 UI 已按未合并数据渲染。
**规避**：在 `buildCombatDataFromYAML` 返回 `true` 后、`initUI()` 前同步调用 `applyPersistedRoster()`。

## 7. 测试方法

### 7.1 环境准备
1. SillyTavern + 酒馆助手扩展（前端依赖酒馆助手运行，无降级）。
2. 浏览器 DevTools 控制台，确认 `getVariables({type:'chat'})` 与 `insertOrAssignVariables` 可用。

### 7.2 核心测试用例

**T1 首次保存落盘**
- 打开技能编辑器 → 修改某角色技能 → 点"保存"。
- 控制台：`getVariables({type:'chat'})['rpg_combat_roster']` 应包含该角色及修改后的技能。
- 应在聊天 JSON 的 `chat_metadata.variables` 中出现（DevTools 查看该聊天 `.jsonl` 文件）。

**T2 清空 combatstatus + 刷新后仍在**
- 保存后，清空 `combatstatus`、刷新页面，重新粘贴相同 `<Combat_block>`。
- 同名角色应加载为**保存后**的技能（而非 Combat_block 原版）。

**T3 新建聊天后消失**
- 酒馆新建一个聊天对话，重新粘贴 `<Combat_block>`。
- 角色技能应回到 Combat_block 默认版（无持久化数据）。

**T4 合并：同名角色不同技能**
- 保存角色 A 的修改版技能集。
- 新 `<Combat_block>` 送来角色 A 的旧版技能 → 加载后应为保存版（持久化优先）。

**T5 合并：同名角色在持久化中不存在**
- 新 `<Combat_block>` 送来一个从未保存过的角色 B → 用 Combat_block 默认技能。

**T6 战斗进行中保存**
- 战斗中角色 A 已半血 → 打开编辑器点保存 → 返回战场，A 的 HP 不应被重置为满（配置覆盖，不覆盖当前 HP）。

**T7 酒馆助手不可用（已被删除的降级场景）**
- 无需测试。前端无酒馆助手无法运行，持久化直接调用 `insertOrAssignVariables`/`getVariables`，无兜底。

**T8 增删技能**
- 新增技能 → 保存 → 刷新 → 应存在；删除技能 → 保存 → 刷新 → 应消失。

### 7.3 回归测试
- 防御恢复设置持久化（`DEFEND_VAR_KEY`）不受影响。
- 敌方技能/Chat 战斗逻辑不回归。
- 控制台零报错。
